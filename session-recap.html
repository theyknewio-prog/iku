Légal — Contenu interdit

5 fixes

Les filtres de contenu interdit (mineurs) avaient des trous. Pas évident à voir, mais fatal pour un site adulte si on se fait choper. Maintenant bétonné à 5 niveaux.

Risque légal
🛡️Le filtre ne regardait que 1/4 des champs
❌
Le filtre vérifiait seulement les tags d'une vidéo. Mais les sources mettent aussi les noms des personnages, les séries, et le titre dans d'autres champs. Un contenu banni pouvait passer si le mot interdit était dans le titre et pas dans les tags.
✅
Maintenant le filtre vérifie tags + personnages + séries + titre + slug. Un mot banni n'importe où = la vidéo est bloquée.
Risque légal
📺Les vidéos "Up Next" étaient pas filtrées
❌
Sur les pages vidéo, la section "More like this" et "Up Next" appelait une autre API qui ne passait pas par le filtre. 78% des pages vidéo étaient concernées.
✅
Remplacé par une nouvelle fonction qui cherche dans ta base avec le filtre actif. Bonus : les suggestions sont maintenant vraiment liées au personnage de la vidéo.
Risque légal
🕳️2 sources queryaient la DB sans filtre
❌
Les fichiers qui gèrent Rule34Video (277K vidéos) et les sites WordPress lisaient directement la base sans appliquer aucun filtre anti-contenu-banni.
✅
Filtre ajouté au niveau SQL sur toutes les requêtes. Plus de contournement possible.
Risque légal
🔒Le safety net du scraper avait le même trou
❌
Le dernier rempart qui vérifie avant d'écrire en base ne checkait qu'1 colonne sur 3. Si le premier filtre rate, ce dernier rempart laissait aussi passer.
✅
Le safety net vérifie maintenant les 3 colonnes d'arrays + le slug + le titre.
Risque légal
🧹Les appels "live" à Danbooru passaient à travers
❌
Certaines fonctions appelaient directement l'API Danbooru en live (contournant ta base et son filtre). Les résultats arrivaient bruts côté utilisateur.
✅
Tous les appels live passent maintenant par le filtre JavaScript avant d'être renvoyés. Ceinture + bretelles.

Argent — Paiements Stripe

10 fixes

Le tunnel de paiement avait 6 blockers qui empêchaient les gens de payer ou qui causaient des pertes d'argent silencieuses. Les plus graves corrigés maintenant.

Bug argent
💸Tes meilleurs users ne pouvaient pas payer
❌
Le coupon "-30% Waifu Scholar" (offert aux users tier 5) crashait le checkout. Stripe refusait la combinaison d'options que j'avais demandée. Les 100% des users visés par la promo ne pouvaient PAS acheter Pro.
✅
Changé pour envoyer le coupon tout seul, sans l'autre option qui entrait en conflit. Checkout fonctionne maintenant pour les Waifu Scholar.
Bug argent
♾️Les lifetime pouvaient perdre leur statut
❌
Un user achète Lifetime (70€). Dans les heures qui suivent, un ancien webhook mensuel arrive en retard et écrase silencieusement le statut lifetime en mensuel. L'user avait payé 70€ pour à vie et voyait "plan mensuel — expire dans 30 jours".
✅
Ajout d'une garde : si pro_status = lifetime, aucun webhook ne peut downgrade. Plus on annule automatiquement tout ancien abonnement au moment de l'achat lifetime.
Bug argent
📅Les annuels étaient classés mensuels
❌
Le code qui reconnaît quel plan a été acheté cherchait le mot "year" dans l'ID de prix Stripe. Problème : les IDs Stripe sont des chaînes aléatoires qui ne contiennent jamais "year". Tous les abonnements annuels étaient donc classés mensuels. Facturation OK mais l'UI disait mensuel.
✅
Remplacé par une comparaison exacte avec les IDs configurés dans les variables d'environnement.
Bug argent
🕳️Paiements perdus dans les erreurs
❌
Si la base de données avait un hoquet de 3 secondes au moment d'un webhook Stripe, le code log l'erreur mais renvoyait OK à Stripe. Résultat : paiement reçu, Pro pas activé, Stripe ne retry jamais. Perte totale du paiement.
✅
Maintenant on retourne une erreur 500 en cas de problème. Stripe retry automatiquement pendant 3 jours. Plus de paiements silencieusement perdus.
Bug argent
👻"J'ai payé mais rien ne change"
❌
Après un paiement réussi, l'user atterrissait sur /profile mais la page ne montrait aucun changement. Zéro indication qu'il est maintenant Pro. Support ticket garanti : "Est-ce que mon paiement est passé ?"
✅
Nouveau banner "Welcome to Pro ✨" avec le plan acheté et la date de renouvellement. Plus un badge permanent "iku.gg Pro" visible en haut de la page profil.
Bug argent
💳Pas d'email quand la carte est refusée
❌
Quand la carte d'un user Pro est déclinée à la prochaine facturation, il ne reçoit aucune notification. Son Pro finit par être coupé et il blâme le site.
✅
Email automatique qui lui explique qu'il y a un souci avec sa carte et lui donne un lien pour la mettre à jour. Envoyé 1 fois max par semaine (pas de spam).
Bug argent
🎯Double-clic = 2 paiements
❌
Un user qui double-clique rapidement sur "Get Pro" créait 2 sessions Stripe en parallèle. Risque théorique de se faire facturer 2 fois.
✅
Ajout d'une clé d'unicité : dans une fenêtre d'1 minute, les clics multiples retournent la même session. Stripe refuse les doublons.
Bug argent
🚫Un déjà-Pro pouvait racheter un plan
❌
Un user lifetime pouvait par erreur acheter un plan mensuel en plus. Résultat : facturation double + bug de statut mélangé dans la base.
✅
Le serveur refuse maintenant le checkout (erreur claire) si l'user a déjà lifetime ou déjà le même plan actif.
Bug argent
🏃Paiement via portail Stripe oublié
❌
Si un user changeait de plan via le portail Stripe (pas via notre checkout), le webhook arrivait sans les infos utilisateur. On ne savait pas à qui appliquer le changement, on le droppait silencieusement. User payé mais Pro pas synchro.
✅
On retrouve maintenant l'user via son Stripe customer ID en fallback. Plus de webhooks orphelins.
Bug argent
⚡past_due en retard = UI menteuse
❌
Quand un paiement échouait, le flip vers "past_due" attendait un autre webhook de Stripe qui pouvait arriver des minutes après. Entre-temps l'UI continuait à dire "Actif".
✅
On flippe immédiatement le statut à past_due sur l'échec de paiement. UI toujours synchro.

Expérience utilisateur — gros bugs

14 fixes

Les bugs UX les plus critiques. Le premier est énorme : la majorité de ton catalogue était invisible pour les visiteurs.

Bug UX
📚96% du catalogue était invisible
❌
Les pages /trending, /new, /tag, /character, /series n'affichaient que les 17K vidéos Danbooru. Les 336K autres vidéos (Rule34Video, Gelbooru, WP) étaient totalement invisibles. Un visiteur clique sur un tag, voit presque rien, et se barre.
✅
Les 5 pages interrogent maintenant ta base PostgreSQL complète. Le visiteur voit TOUT ton catalogue, soit 20x plus de contenu qu'avant.
Bug UX
🔊Son de la watch page cassé
❌
Cliquer sur "Unmute" ne faisait rien. Seule la molette marchait sur desktop, rien sur mobile. 3 bugs différents en cascade : React qui réappliquait l'état, un overlay invisible qui bouffait les clics, et un bouton qui ouvrait un popup au lieu de toggle le son.
✅
Les 3 bugs réglés en cascade et vérifiés en prod avec un test automatisé (Playwright) : clic = son activé, vidéo continue à jouer.
Bug UX
♾️Shorts scroll bloqué après 10 vidéos
❌
Le feed Shorts chargeait 20 vidéos, le filtre serveur en gardait 3-5, et l'infini scroll n'avançait jamais au lot suivant. L'user tapait un mur après ~10 swipes.
✅
Lot plus large (60 vidéos), avancement toujours, et nouveau filet de sécurité qui déclenche un fetch automatique quand le buffer devient bas. Testé : 954 vidéos en 20 rounds de scroll sans blocage.
Bug UX
❤️Like/Save des Shorts = fake
❌
Les boutons Like, Save, et le heart-burst (double-tap) sur les Shorts étaient 100% frontend. L'user tappe Save → rien ne part sur le serveur → rien dans ses favoris quand il revient. Core feature TikTok-style = mensonge UI.
✅
Les 3 actions appellent maintenant ton API favoris, synchronisent localStorage ET la base. Plus un score event pour la gamification. Hydratation de l'état initial pour que les déjà-likés apparaissent en rouge dès le chargement.
Bug UX
🔄Supprimer un favori le réajoutait
❌
User connecté sur un nouveau device, page favoris, clic sur le cœur pour retirer. Le code faisait un DELETE serveur → puis appelait toggleFavorite sur localStorage (vide sur ce device) → qui AJOUTAIT le favori localement et faisait un POST. Fantôme qui revient au refresh.
✅
Nouvelle fonction "removeFavorite" qui ne fait que retirer, jamais ajouter. Plus de race condition.
Bug UX
🔍Bouton Search mobile allait sur /explore
❌
Sur mobile, taper l'icône loupe de la bottom nav redirigeait vers /explore (une page de browse) au lieu d'ouvrir un champ de recherche. L'input n'existait que dans le drawer hamburger caché. Quasi impossible de search sur mobile.
✅
Nouvelle page /search dédiée avec le champ autofocusé au chargement. Clavier pop automatiquement sur mobile.
Bug UX
⌨️Touche Espace bloquait les boutons
❌
Sur la page watch, si l'user tabulait pour sélectionner un bouton au clavier et appuyait Espace pour l'activer, le raccourci vidéo globale volait la touche et mettait la vidéo en pause à la place. Accessibilité clavier complètement cassée.
✅
Le raccourci ignore maintenant Espace et Entrée quand un bouton ou un lien a le focus.
Bug UX
🖼️19,640 thumbnails cassées
❌
11% des images sur /explore et /character étaient cassées. Cause : 19,640 lignes en base pointaient vers gelbooru.com/thumbnails/… qui retourne 404. La bonne URL était img3.gelbooru.com/thumbnails/….
✅
Migration SQL one-shot qui a réécrit les 19,640 URLs d'un coup. Plus les patterns remotePatterns de Next.js mis à jour pour éviter qu'une nouvelle image casse.
Bug UX
📐Topbar recouvrait le contenu
❌
Sur toutes les pages hors homepage, la topbar fixe écrasait le haut du contenu. Seulement 4 pages avaient le padding-top correct, les autres étaient cassées.
✅
Padding déplacé au niveau global. Toutes les pages respectent maintenant la topbar.
Bug UX
📱Nav mobile incomplète
❌
Sur mobile, pas de hamburger dans la topbar. L'accès au drawer de nav passait uniquement par le bouton "More" de la bottom nav. Les liens Blog/Pricing/Glossary étaient introuvables.
✅
Hamburger ajouté dans la topbar mobile. Nouveau drawer complet en 5 sections (Discover, Library, Browse, More, Quick Tags). Body scroll lock pendant l'ouverture.
Bug UX
🎨Pages vides sans images
❌
/character, /series, /history, /explore affichaient des placeholders tristes (gradients gris, emojis initiales) au lieu de vraies images. Le site avait l'air vide alors que tu as 353K vidéos.
✅
Vraies thumbnails partout, fetch par batch via getThumbnailsForTags (mémoïsé 1h donc zero coût réseau sur cache chaud).
Bug UX
✉️Double counter "online now" sur mobile
❌
Sur mobile on voyait "1,247 online" en dur au-dessus du hero, puis un OnlineCounter live en dessous. Deux compteurs qui se contredisaient.
✅
Le compteur statique a été remplacé par le live, le doublon supprimé.
Bug UX
🔎Search sans résultats = page morte
❌
Quand l'autocomplétion renvoyait 0 résultats, le dropdown se fermait silencieusement. L'user pensait que la barre était cassée.
✅
Dropdown reste ouvert avec un message "Aucun résultat — appuie sur Entrée pour chercher quand même".
Bug UX
💬Messages d'erreur cryptiques
❌
Les toasts sur la page profile utilisaient du pattern matching sur le texte pour décider de la couleur. "Username already taken" était affiché en vert comme si c'était un succès.
✅
Refactor pour passer un type explicite (success/error) au lieu de deviner.

Sécurité

9 fixes

Failles de sécurité identifiées par l'audit. Certaines étaient théoriques (attaques sophistiquées), d'autres exploitables tout de suite.

Sécurité
🎭Vol de compte via Discord
❌
Un attaquant pouvait : (1) créer un compte iku avec ton email, (2) ne jamais vérifier l'email, (3) puis OAuth Discord avec un compte Discord qui a le même email. Le code liait automatiquement sans rien vérifier — accès complet au compte cible (favoris, Pro, Stripe customer).
✅
L'auto-link Discord refuse maintenant de lier à un compte non vérifié. Plus, Discord lui-même doit avoir vérifié l'email côté Discord (profile.verified = true).
Sécurité
📧Majuscules = 2 comptes
❌
La contrainte unique sur l'email était sensible à la casse. Alice@x.com et alice@x.com créaient 2 comptes différents. Le login utilisait LOWER(...) donc retournait un des deux au hasard. Pollution + squatting trivial.
✅
Nouvelle contrainte unique case-insensitive (LOWER(email)) via migration SQL one-shot. 0 doublon trouvé en prod au moment de la migration.
Sécurité
🏁Race sur token reset password
❌
Si un attaquant interceptait le token de reset password, il pouvait faire une course avec le user légitime. Les 2 requêtes en parallèle passaient le check "not used", les 2 faisaient le hash, les 2 updateaient. Last-write-wins = attaquant gagne.
✅
Transition atomique : UPDATE ... RETURNING qui marque used_at et retourne user_id en une seule opération. 2e requête se fait jeter.
Sécurité
🎯Phishing via Stripe checkout
❌
Le code de checkout utilisait le header "Origin" envoyé par le browser pour construire les URLs de retour Stripe. Un attaquant pouvait forcer "Origin: evil.gg" et faire en sorte que Stripe redirige la victime vers un site de phishing après un vrai paiement.
✅
URLs construites à partir de NEXT_PUBLIC_SITE_URL (constante serveur non-modifiable).
Sécurité
🧱Protection XSS renforcée
❌
Le Content-Security-Policy laissait passer 'unsafe-eval' et 'unsafe-inline'. Si jamais un bug introduit une faille XSS (injection de HTML), l'attaquant peut exécuter n'importe quel JavaScript et voler la session.
✅
'unsafe-eval' supprimé. Nouveau middleware qui génère un nonce (128 bits aléatoires) par requête, et chaque script inline doit avoir ce nonce pour s'exécuter. Défense active contre XSS.
Sécurité
📊Rate limiter infini
❌
/api/resolve avait un rate limiter avec une map qui pouvait grossir à l'infini. Un botnet avec plein d'IPs différentes pouvait faire consommer toute la RAM du serveur.
✅
Plafond dur à 10K entrées avec éviction FIFO. Plus, factorisation de tous les rate limiters du site (9 duplications) dans un seul helper partagé et borné.
Sécurité
🔑Mots de passe plus résistants
❌
bcrypt rounds = 10 (minimum 2026 pour un site adulte/paiement = 12).
✅
Upgradé à 12 rounds sur signup, change password, et reset password. Coût CPU 4x plus élevé pour l'attaquant qui tente un brute force.
Sécurité
🚰DoS sur /api/video-stream
❌
Le proxy vidéo n'avait pas de rate limit et pouvait saturer la bande passante Hetzner (20TB/mois). Un attaquant pouvait faire 100 requêtes parallèles avec des vidéos lourdes = facture qui explose.
✅
Rate limit 30/min/IP ajouté + try-catch sur les erreurs upstream + timeout 20s.
Sécurité
🗝️Clés API brûlées en git history
⚠️
Les clés Gelbooru et Rule34 sont dans l'historique Git public (legacy). La clé Rule34 a été rotée une fois mais re-committée. Les 2 sont considérées brûlées.
📝
Documenté dans l'audit. Action humaine requise : re-rotation + git filter-repo pour purger l'historique, OU considérer comme publiques et mettre en place un rate limiting côté API.

Performance

5 fixes

Optimisations qui rendent le site plus rapide et plus tenable à l'échelle.

Performance
🐢Watch page lente à cause d'API externes
❌
Chaque affichage d'une page /watch faisait 3 à 5 appels en live à l'API Danbooru (limité à 5 req/sec par leur rate limit). Cold render = 600ms à 1,5 seconde de latence pour récupérer les infos + les vidéos liées.
✅
Nouvelle fonction getDanbooruVideo qui lit d'abord dans ta base PostgreSQL (~5ms) et ne fallback sur Danbooru live que pour les posts pas encore scrapés. Sur 99% des requests : 200-1500ms → 5ms.
Performance
📄Pagination feed lourde à scale
❌
/api/feed utilisait LIMIT/OFFSET pour la pagination. Sur 351K rows, un OFFSET 300000 = le serveur doit skipper 300K lignes à chaque requête. Catastrophe à scale.
✅
Remplacé par keyset pagination (curseur composite). Le serveur saute directement à la bonne position via l'index, O(log n) au lieu de O(n). Validé en prod : page 1 → curseur → page 2 → nouveau curseur, 60 vidéos à chaque fois.
Performance
🗑️124 MB de code mort
❌
5 fichiers JSON legacy de l'ancienne archi (pré-migration PostgreSQL) traînaient dans le repo : videos.json (12M), gelbooru (10M), rule34 (11M), rule34video (84M), wp-hentai (4M). Total 124 Mo cloné à chaque git clone, chaque deploy Docker.
✅
Les 5 fichiers supprimés. Le script de migration marqué historique. Déploiements Docker plus légers.
Performance
🔄Routes dynamiques vs statiques
❌
Next.js 16 a un piège : une route /watch/[slug] sans generateStaticParams est traitée comme 100% dynamique. Chaque hit = full render + query DB. L'optimisation ISR ne marchait pas.
✅
Couche de cache applicative (memoize 5 min) + cache L2 PostgreSQL (1h) pour les URLs résolues. Warmup loop interne qui précharge les 500 top vidéos toutes les 30 min.
Performance
📚Fichiers monstres organisés
❌
WatchPlayer.tsx = 1715 lignes, globals.css = 9463 lignes. Difficile à naviguer, facile de casser par accident.
✅
WatchPlayer → icônes et helpers extraits dans un fichier séparé (1715 → 1549 lignes). globals.css → table des matières de 48 sections avec numéros de ligne en tête de fichier (split physique trop risqué à cause de la cascade CSS).

Qualité du code

4 fixes

Fondations qui facilitent les futurs développements et évitent les régressions.

Code quality
✅Premier framework de tests du repo
❌
Zero test dans le projet avant. Chaque changement de code critique (Stripe, auth, DB) était un saut dans le vide.
✅
vitest installé + 21 tests unitaires sur le webhook Stripe (201ms pour tout faire passer). Couverture des 10 blockers argent : reconnaissance de plan, garde lifetime, fallback customer ID, past_due mapping, annulation de prior sub, tolérance aux erreurs Stripe.
Code quality
🔧Rate limiter factoré
❌
9 routes différentes dupliquaient le même code de rate limiting avec des variations subtiles. Certaines avaient des caps, d'autres non. Chaque nouvelle route = copie-coller avec risque de bug.
✅
Extraction dans src/lib/rate-limit.ts — un seul helper partagé avec API simple (createRateLimiter + consume). Les 9 routes migrées. Impossible d'introduire un bug variant par inadvertance maintenant.
Code quality
🔕15 erreurs silencieuses exposées
❌
15 endroits dans le code avec .catch(() => {}). C'est-à-dire que si une opération plante, on swallow l'erreur et personne ne voit rien. Un était un vrai bug (clearHistory serveur qui ne clearait pas vraiment).
✅
Le vrai bug corrigé (log d'erreur). Les 14 autres (rejections normales de l'API browser comme play() quand autoplay est bloqué) ont maintenant un commentaire explicite qui explique pourquoi c'est intentionnellement silencieux.
Code quality
📝Documentation inline massive
❌
Beaucoup de code sans commentaire. Revenir dessus dans 6 mois = devoir re-raisonner le pourquoi.
✅
Chaque fix commente le pourquoi (bug qu'on évite, audit qui l'a trouvé, contrainte qui le motive). Plus une grosse section "Silent bugs" dans CLAUDE.md qui documente les pièges à ne pas reproduire (React muted quirk, autoplay race, Next.js 16 ISR gotchas, etc.).

Session complète : audit profond (7 rapports parallèles + 130+ findings) → 6 commits → 6 déploiements Coolify → 2 migrations SQL prod.
