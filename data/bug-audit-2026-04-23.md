# iku.gg bug audit — 2026-04-23

Scope: all `src/app/api/**`, `src/lib/**`, `src/auth.ts`, `src/middleware.ts`, scripts, and selected pages. Known bugs catalogued in both CLAUDE.md files were skipped.

Summary: 14 bugs (P0:4, P1:4, P2:4, P3:2) + cross-cutting concerns.

---

## P0 — Security / compliance (4 bugs)

### B1. [scripts/scrape-gelbooru.ts:16-18, scripts/scrape-rule34.ts:16-18] Clés API live hardcodées dans le repo

**What**: Les deux scrapers contiennent encore des `API_KEY = "3ed16caf49d5..."` (Gelbooru) et `"f230feb40110c..."` (Rule34), avec les `USER_ID`. Les autres scripts + `src/lib/gelbooru.ts` / `rule34.ts` utilisent `process.env.*`. Contredit CLAUDE.md qui prétend que la clé Rule34 a été régénérée 2026-04-03 et que les secrets sont passés en env. C'est documenté comme "C1/C2 CRITICAL" dans `.audit/supply-chain.md` mais jamais corrigé.
**Why**: Repo privé ne compte pas — Coolify clone via HTTPS, n'importe quel collab / fuite git pack / backup mal rangé = compromission. Les GitHub Actions utilisent déjà `GELBOORU_API_KEY` / `RULE34_API_KEY` en secrets, donc supprimer les constantes ne casserait rien en prod.
**Fix**: Remplacer par `const API_KEY = process.env.RULE34_API_KEY ?? "";` (pattern déjà en place côté `src/lib`). Régénérer la clé Rule34 côté rule34.xxx une fois le code propre.

### B2. [src/app/api/mark-dead/route.ts:21-48] Endpoint non-authentifié peut marquer des vidéos comme mortes en masse

**What**: `POST /api/mark-dead` accepte un slug, rate-limite à 20/min/IP, aucune auth. Chaque succès met `dead_at = NOW()` donc la vidéo disparaît de toutes les listes (`dead_at IS NULL` filter dans `getVideos`).
**Why**: Un botnet de 1000 IPs = 20 000 vidéos/min marquées mortes. Le scanner `dead-video` (source-side) ne ré-active pas automatiquement, donc une attaque vide silencieusement la moitié du catalogue. Aucune signature / pas de vérification que le browser a vraiment reçu un `error` event.
**Fix**: (1) Vérifier que la requête vient d'une vraie lecture (nonce signé envoyé par /watch rendu côté serveur, expiré 5min). Ou (2) maintenir un compteur `dead_reports` qui nécessite ≥3 reports distincts d'IPs différentes dans les 24h avant de flipper `dead_at`. Ou (3) faire ça depuis un script cron qui scanne lui-même et pas le browser.

### B3. [src/app/api/video-stream/route.ts:136-173] Aucun check banned-content sur URL arbitraire

**What**: L'endpoint accepte n'importe quelle `page_url` pointant vers un hostname allowlisté (rule34video.com, hentaicity.com, etc.), fetch depuis notre IP, stream. **Rien ne vérifie** que la page cible n'est pas du contenu banni.
**Why**: Un attaquant peut forger `GET /api/video-stream?url=https://rule34video.com/videos/banned-loli-slug/` et le serveur iku.gg fetch + stream le contenu depuis son IP. iku devient intermédiaire légal pour du contenu illégal. L'URL ne passe par aucun `containsBannedContent` — ce check existe uniquement sur les rows en DB. Risque 2257/DMCA.
**Fix**: Avant `fetch(streamUrl)`, extraire slug/id de la page_url, lookup en DB : si row existe et `containsBannedContent(row)` ou `dead_at IS NOT NULL` → 403. Si row n'existe pas en DB → 404 (on ne proxy que du contenu qu'on a ingéré et validé).

### B4. [src/auth.ts Credentials provider lignes 162-186] Zéro rate-limit sur le login

**What**: `/api/auth/callback/credentials` (route NextAuth interne) n'a aucun rate-limit. `forgot-password` est à 5/h/IP, `signup` à 5/h/IP, mais le login brute-force est libre.
**Why**: Credential-stuffing classique. `bcrypt.compare` avec 12 rounds ≈ 150ms — un attaquant peut tester ~400 mots de passe/min contre un email leaked. Multi-IPs = infini.
**Fix**: Ajouter une middleware rate-limit sur `/api/auth/callback/credentials` dans `middleware.ts`, ou wrap `authorize()` dans `auth.ts` avec un compteur PG par email (`SELECT count FROM login_attempts WHERE email=$1 AND window > NOW()-5min`) → 429 après 10 échecs/5min/email. Pattern similaire à ce que fait déjà `password_reset_tokens` atomiquement.

## P1 — Breaks user flow (4 bugs)

### B5. [src/app/api/auth/reset-password/route.ts:12-63] Aucun rate-limit sur reset-password

**What**: Contrairement à `forgot-password` (5/h), `reset-password` accepte des `{token,newPassword}` sans limiter. Token length check `>= 32` + update atomique via `used_at IS NULL` protège contre la réutilisation, mais pas contre la force-brute du token.
**Why**: Si un token fuite partiellement (ex. via log serveur, referrer leak, navigateur multi-onglets), un attaquant peut tenter des complétions. 64-hex chars = 256 bits, donc la brute-force pure est inabordable, mais side-channel timing sur la query PG (`UPDATE ... WHERE token=$1`) reste une cible pour un attaquant patient. Tout endpoint qui hit PG sans rate-limit = fenêtre de DoS.
**Fix**: Reutiliser `createRateLimiter({ name: "reset-password", max: 10, windowMs: 3600_000 })` comme `forgot-password`.

### B6. [src/app/api/profile/password/route.ts:10-62] Aucun rate-limit sur le changement de password

**What**: `POST /api/profile/password` vérifie `currentPassword` via `bcrypt.compare` mais n'a aucun rate-limit.
**Why**: Une session XSS'ée ou volée (cookie) peut brute-force le mot de passe courant à volonté — 150ms × N tentatives illimitées. Contournable via cookie jacking, pas via credential stuffing direct, mais significatif vu que l'ID session NextAuth JWT vit 30 jours.
**Fix**: `createRateLimiter({ name: "pwd-change", max: 5, windowMs: 3600_000 })` keyé sur `session.user.id`.

### B7. [src/app/api/history/route.ts:31-72] Aucun rate-limit + bulk 500 sans email-verify gate

**What**: `POST /api/history` accepte `bulk: [500 slugs]` sans rate-limit et SANS le gate email-verify qui existe sur `/api/favorites`. `/api/favorites bulk` (line 49-60) vérifie `vStatus.passed` avant d'accepter l'import; `/api/history bulk` non.
**Why**: Un compte fraîchement créé mais non vérifié (spam signup) peut inonder `user_history` de 500 slugs × N fois. La table PG gonfle, le leaderboard peut biaiser si un badge est attaché au nombre d'items.
**Fix**: Symétrie avec favorites — appeler `getVerifyStatus(session.user.id)` avant d'accepter `bulk`. Ajouter un rate-limit 10/min/user.

### B8. [src/app/api/resend-verification/route.ts:28-31] setInterval sans unref

**What**: `setInterval(cleanup, 10 * 60_000)` sans `.unref()`. Même pattern que `rate-limit.ts` (qui a `unref`) ou `memo.ts` (qui ne l'a pas mais n'est pas si grave).
**Why**: En dev / hot-reload / hors-Coolify, le process Node ne peut pas exit proprement car le timer le garde vivant. `npm test` qui importe ce module en background ne se termine jamais. Minor en prod (le container tourne ad vitam) mais empoisonne DX.
**Fix**: Ajouter `if (typeof (timer as unknown as {unref?: () => void}).unref === "function") timer.unref();` (même pattern qu'ailleurs dans le codebase).

## P2 — Edge cases (4 bugs)

### B9. [src/app/api/video-stream/route.ts:230] `b-cdn.net` en allowlist = SSRF vers n'importe quel tenant Bunny

**What**: `b-cdn.net` est Bunny CDN multi-tenant — `hostname === "b-cdn.net" || hostname.endsWith(".b-cdn.net")` autorise `*.b-cdn.net`, donc n'importe quel client Bunny peut pointer son pull-zone vers iku. Même logique pour `workers.dev` côté CSP (feed/route.ts:115).
**Why**: Un attaquant crée `evil-uploader.b-cdn.net`, héberge n'importe quel fichier MP4 (légal ou pas), puis force le serveur iku à streamer. iku devient bandwidth-proxy + masque l'IP source. Différent de B3 parce qu'il n'y a même pas besoin d'une vraie page — directement un `.mp4` sur un CDN public.
**Fix**: Restreindre à `vz-*.b-cdn.net` (pattern porn3dx documenté en commentaire) via regex au lieu de `endsWith`. Ou lister explicitement les ~10 sous-domaines Bunny utilisés par porn3dx.

### B10. [src/lib/memo.ts:121-135] setInterval sans unref + potentielle cross-module memory leak

**What**: Le cleanup timer global à la fin du module n'a pas `unref()`. Le check `!entry.promise && !entry.hasValue` en ligne 127 ne supprime que les entrées cold-failed, pas les stale entries avec `hasValue: true`. Résultat: si la TTL expire et aucun caller ne re-déclenche la clé pour provoquer un refresh, l'entrée vit éternellement (jusqu'à cap MEMO_MAX_SIZE).
**Why**: Pas critique — le cap 500 protège. Mais pour des clés rares (ex. `thumb-for-tag` avec un tag unique appelé une seule fois), on garde la mémoire sans raison.
**Fix**: Dans le cleanup, supprimer aussi `entry.expiresAt < now - 24h && !entry.promise` (expired+abandoned). Ajouter unref.

### B11. [src/app/tag/[tag]/page.tsx + series + character] `revalidate = 3600` sur route `force-dynamic` = dead config

**What**: Toutes les routes taxonomy font `export const dynamic = "force-dynamic"; export const revalidate = 3600;` en disant en commentaire "force-dynamic because awaiting searchParams". Next.js 16 ignore `revalidate` quand `dynamic === "force-dynamic"` — CLAUDE.md le documente déjà (`reference_isr_searchparams_conflict`).
**Why**: Pas un bug comportemental, juste config dead. Peut induire Sab en erreur quand il lit le fichier ("ah 1h de cache ISR sur /tag — non, zéro").
**Fix**: Supprimer `export const revalidate = 3600` sur ces routes, ou ajouter un commentaire explicite "ignored, see feedback_isr_searchparams_conflict". Pas de changement runtime.

### B12. [src/app/layout.tsx:117] `nonce={nonce}` sur le JSON-LD inline alors que `getNonce()` return undefined

**What**: Depuis csp-nonce.ts est stubbé à `return undefined`, l'attribut `nonce={undefined}` sur un `<script>` est un no-op côté React (pas rendu). Mais le code est partout (`layout.tsx`, `watch/[slug]`, `tag/[tag]`, `character/[slug]`, `series/[slug]`, `glossary/[term]`, `blog/[slug]`) — donne une fausse impression de sécurité CSP.
**Why**: La CSP actuelle autorise `'unsafe-inline'` donc la présence/absence de nonce ne change rien. Mais si un jour quelqu'un retire `'unsafe-inline'` en pensant que les nonces prennent le relais, **tous** les JSON-LD inline seront cassés silencieusement (pas d'erreur visible — Google juste ne verra plus le schema).
**Fix**: Soit supprimer tous les `nonce={nonce}` (le commentaire dans csp-nonce.ts est clair), soit réactiver le nonce MAIS seulement en retirant aussi `'unsafe-inline'` de CSP. Mix actuel = trap.

## What's looking good (anti-panique)

- **`filterBannedContent` + `BANNED_TAGS_ARRAY`** : appliqué systématiquement côté SQL ET JS dans content.ts et tous les source-modules (hentaicity, eporner, sfmcompile, generic-source, 3dhentaitube). Belt-and-suspenders propre. Le upsertVideos safety net dans scripts/db.ts est ceinture + bretelle.
- **SQL injection** : zéro string-concat SQL. Tous les call-sites utilisent des placeholders `$N`. Même le WHERE clause dynamique de `_getVideos` réutilise des indexes numériques sans interpolation user-controlled.
- **IP detection** : `getClientIp` prend `x-real-ip` puis `x-forwarded-for.pop()`, jamais `[0]`. Applied consistently dans rate-limit.ts, les routes API, et les taxonomy pages.
- **Stripe webhook** : signature verify → dedup read → process → dedup insert AFTER success. Handler idempotent. Guard `pro_status != 'lifetime'` partout dans l'UPDATE. handler retourne 500 sur erreur pour que Stripe retry.
- **Rate limiter atomicité** : pattern `get → check → increment` est vraiment atomique en Node mono-thread (documenté, pas un "faux positif" comme certains audits passés l'ont cru).
- **password reset atomic claim** : `UPDATE ... WHERE token=$1 AND used_at IS NULL RETURNING user_id` empêche la double-consommation.
- **unlock-video** : transaction BEGIN/COMMIT avec `UPDATE user_stats SET score = score - $2 WHERE score >= $2` — pas de double-spend possible.

## Cross-cutting concerns

1. **Rate-limit coverage** : 14 routes API, seulement 7 ont un rate-limit (proxy, resolve-video, video-stream, resolve, feed, signup, forgot-password, mark-dead, vast-stream, score, checkout). Manquent : reset-password, profile, profile/password, history, favorites, auth/callback (le plus critique — B4), verify, resend-verification (a sa propre cooldown mais que par user, pas par IP), unlock-video, pro-status, user/stats, user/quests, geo, health. Le score/checkout sont keyés user (OK) mais le reste devrait être keyé IP.

2. **Timer unref pattern inconsistant** : `rate-limit.ts` unref correct, `resolve-video/route.ts` et `video-stream/route.ts` unref correct, `memo.ts` et `resend-verification/route.ts` non. Standardiser via un helper `safeInterval(cb, ms)` qui unref toujours.

3. **Dead-video marking surface trop large** : `/api/mark-dead` + le scanner cron + le player onError = 3 chemins pour `dead_at`. Au minimum le player devrait envoyer une preuve (nonce signé issued à la fabric de la page) pour que le vote compte.

4. **Leftover ads** : 4 fichiers + ~50 CSP hosts à nettoyer (B13). Tant que Sab n'a pas confirmé "ok nuke complet", les routes `/api/vast*` et `ad-config.ts` restent live. Re-vérifier avant prochain déploy que `grep -r "AD_ZONES\|HILLTOPADS\|ExoClick" src/` retourne zéro.

5. **CSP `'unsafe-eval'`** : présent à cause d'ExoClick — maintenant qu'ads sont nukées, c'est retirable. Un simple `script-src 'self' 'unsafe-inline' https://...` sans `'unsafe-eval'` rendrait XSS dramatiquement plus dur (empêche `eval`, `new Function`, `setTimeout(string)`).

6. **`revalidate` + `force-dynamic`** : B11, 6-7 pages taxonomy. Pas dangereux, juste confusing.
